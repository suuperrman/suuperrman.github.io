LangChain学习笔记

一、基础概念与架构

1.核心定位

LangChain 是一个用于开发大语言模型（LLM）应用的框架。它提供了模块化、可插拔的组件，让开发者可以快速构建复杂的 LLM 应用，而无需从零开始实现每一个环节。

概念说明：LangChain 的核心思想是将 LLM 应用开发中的常见功能（提示词管理、模型调用、数据检索、对话记忆、工具调用等）抽象为标准化组件，通过链式调用（Chains）或代理（Agents）将这些组件组合起来，形成完整的应用。

使用场景：

  • 构建基于大模型的智能对话系统
  • 开发知识库问答应用（RAG）
  • 实现自主决策的 AI 代理
  • 构建文档摘要、翻译、生成等工具
  • 快速验证 LLM 应用原型

注意事项：

  • LangChain 是框架而非模型，本身不提供大模型能力，需要接入第三方 LLM API 或本地模型
  • 版本迭代较快，API 可能发生变化，建议关注官方文档
  • 提供了 Python 和 JavaScript/TypeScript 两种主要语言版本

2.核心组件

LangChain 由六大核心组件构成，每个组件负责特定功能，可以独立使用也可以组合使用。

Models

Models 是 LangChain 与大语言模型交互的接口层，提供统一的 API 来调用不同厂商的模型。

  • LLMs：文本补全模型，输入字符串输出字符串
  • Chat Models：对话模型，输入消息列表（含角色信息）输出消息
  • Embeddings：文本向量化模型，将文本转换为向量表示

Prompts

Prompts 负责提示词的管理与生成，包括模板、示例选择和输出解析。

  • Prompt Templates：提示词模板，支持变量插值
  • Example Selectors：示例选择器，从多个示例中挑选最合适的
  • Output Parsers：输出解析器，将模型输出解析为结构化数据

Indexes

Indexes 处理外部数据的加载、切分、向量化、存储和检索，是 RAG（检索增强生成）的基础。

  • Document Loaders：文档加载器，从各种来源加载文档
  • Text Splitters：文本分割器，将长文档切分为适合向量化的片段
  • Vector Stores：向量数据库，存储和检索向量
  • Retrievers：检索器，从向量库或其他来源检索相关文档

Chains

Chains 是将多个组件按顺序或逻辑组合起来的结构，形成更复杂的处理流程。

  • 基础链：LLMChain、SequentialChain 等
  • 高级链：RetrievalQA、SQLDatabaseChain 等预置链
  • LCEL：LangChain 表达式语言，用管道操作符组合组件

Agents

Agents 是自主决策的智能体，它让 LLM 作为”大脑”，根据用户输入决定调用哪些工具、执行什么操作，最终完成任务。

  • Tools：工具集合（搜索、计算、数据库等）
  • Agent Types：ReAct、Plan-and-Execute 等代理类型
  • AgentExecutor：代理执行器，管理代理的执行循环

Memory

Memory 负责管理对话历史和上下文，让 LLM 应用能够记住之前的交互。

  • 短期记忆：缓冲式记忆，保存最近的对话
  • 长期记忆：基于向量检索或知识图谱的持久记忆
  • 记忆管理：摘要、修剪、压缩等策略

3.架构设计哲学

模块化

LangChain 的每个组件都是独立、可插拔的。你可以替换任何一个组件而不影响其他部分，例如将 OpenAI 模型替换为本地开源模型，将 Chroma 向量库替换为 Pinecone。

可组合

组件可以像搭积木一样组合。简单的应用可以用 LLMChain 把提示词和模型拼起来，复杂的应用可以用 SequentialChain 串联多个链，或者用 Agent 动态决定执行流程。

可观测

LangChain 提供了完整的回调系统，可以追踪每一次模型调用、每一步链执行、每一个工具调用，方便调试和监控。

二、模型 I/O

1.模型接口

LLMs 文本补全模型

LLM 类对应文本补全模型（如 GPT-3 davinci），输入是一个字符串，输出是字符串补全结果。

注意事项：OpenAI 自 GPT-3.5 起主推 Chat Models，纯文本补全模型逐渐减少。新应用建议优先使用 Chat Models。

Chat Models 对话模型

Chat Models 以消息列表作为输入，每条消息带有角色标识（system / human / ai），更适合对话场景。

Embeddings 将文本转换为固定维度的向量表示，语义相近的文本向量距离也相近。

5.检索器（Retrievers）

基础向量检索

MMR 检索（多样性增强）

MMR（Maximal Marginal Relevance）在相关性和多样性之间平衡，避免返回的文档内容过于重复。

多查询检索（MultiQueryRetriever）

自动生成多个不同角度的查询，分别检索后合并结果，提高召回率。

上下文压缩检索

对检索到的文档进行二次处理，只保留与问题最相关的片段，减少无关上下文。

自查询检索（Self-Query）

让 LLM 根据用户问题自动生成元数据过滤条件和文本查询，实现结构化过滤 + 语义检索。

集成检索器（Ensemble）

融合多种检索方式的结果，如关键词检索 + 向量检索，优势互补。

四、链

1.基础链

LLMChain

LLMChain 是最基础的链，将提示词模板、LLM 模型和输出解析器组合在一起。

SimpleSequentialChain

顺序执行多个链，每个链的输出是下一个链的输入（单输入单输出）。

SequentialChain

多输入多输出的顺序链，适合更复杂的场景。

TransformChain

在链中插入自定义转换函数。

2.高级预置链

文档问答链

Stuff（全部填充）

把所有检索到的文档都塞入提示词中，让模型直接基于全部上下文回答。

Stuff 特点：

  • 优点：只调用一次 LLM，答案质量高
  • 缺点：文档太多会超过上下文窗口限制
  • 适用：文档数量少、内容短的场景

MapReduce（分片映射归约）

先对每个文档分别生成答案（Map 阶段），再把所有答案汇总（Reduce 阶段）。

MapReduce 特点：

  • 优点：可处理大量文档，可并行
  • 缺点：多次调用 LLM，成本高；可能丢失细节
  • 适用：文档数量多、内容长的场景

Refine（迭代精炼）

逐个处理文档，每次用上一个文档的答案和新文档一起来精炼答案。

Refine 特点：

  • 优点：答案质量高，逐步完善
  • 缺点：串行执行速度慢，调用次数多
  • 适用：对答案质量要求高的场景

四种文档问答方式对比说明：

方式 思路 LLM调用次数 质量 速度 适用场景
Stuff 全部塞入 1次 高 快 文档少
MapReduce 先分后合 N+1次 中 中（可并行） 文档多
Refine 逐步精炼 N次 高 慢 质量要求高
Map-Rerank 打分排序 N次 中 中 单文档回答

3.表达式语言（LCEL）

核心概念

LCEL（LangChain Expression Language）是 LangChain 推荐的组件组合方式，使用管道操作符 | 将组件串联起来，类似 Unix 管道。

Runnable 接口：所有可组合的组件都实现了 Runnable 接口，提供统一的调用协议（invoke / batch / stream / ainvoke 等）。

核心组件

RunnableSequence（顺序管道）

RunnableParallel（并行分支）

RunnablePassthrough（透传）

RunnableLambda（自定义函数）

RunnableBranch（条件分支）

高级特性

运行时配置

Fallbacks 后备策略

LCEL 的优势：

  • 统一接口：所有组件调用方式一致（invoke / stream / batch / ainvoke）
  • 流式支持：管道中的每一步都原生支持流式输出
  • 异步支持：所有操作都有异步版本
  • 可观测：内置回调支持，便于追踪和调试

八、RAG（检索增强生成）

1.基础 RAG 流程

RAG（Retrieval-Augmented Generation，检索增强生成）是一种将信息检索与大模型生成相结合的技术，通过从知识库中检索相关内容作为上下文，让模型基于检索到的信息回答问题，减少幻觉并提高准确性。

2.高级 RAG 技术

索引优化

多向量检索（Multi-Vector）

为每个文档生成多个向量表示（如原文、摘要、假设问题等），提高召回率。

父文档检索（ParentDocumentRetriever）

检索小块（粒度细、准确），但返回整块父文档（上下文完整）。

假设性问题索引（Hypothetical Questions）

为每段文档生成可能被问到的问题，用问题向量做检索，更匹配用户的提问方式。

摘要索引（Summary Indexing）

为每段文档生成摘要，用摘要做检索，返回原文。

查询优化

查询重写（Query Rewriting）

用 LLM 改写用户的模糊或不完整的问题，提高检索质量。

查询扩展（Query Expansion）

扩展用户问题，生成多个相关查询，分别检索后合并结果。

后退提示（Step-Back Prompting）

让模型先从具体问题”后退”到更抽象的概念/原理，再回答具体问题。

重排序（Reranking）

初筛返回较多候选文档后，用更精确的模型重新排序，提升Top-K的准确率。

多路召回融合：

生成优化

引用溯源（Citation）

让答案标注引用来源，提高可信度。

多文档聚合

当检索到多个相关文档时，让模型综合所有文档生成完整答案。

基础 RAG vs 高级 RAG 对比说明：

维度 基础 RAG 高级 RAG
索引 简单分块 多向量、父子文档、假设问题
查询 直接检索 查询重写、查询扩展、后退提示
排序 向量相似度 重排序、多路融合

1.评估方法论

基准测试

端到端评估

评估整个系统的最终输出质量。

组件级评估

分别评估检索和生成组件，定位瓶颈。

评估维度

维度 说明 评估方式
正确性（Correctness） 答案是否准确 人工标注 / LLM-as-Judge
相关性（Relevance） 答案与问题是否相关 LLM 评分
忠实度（Faithfulness） 是否有幻觉 LLM 校验
有害性（Harmfulness） 是否产生有害内容 规则 + LLM
流畅度（Coherence） 语言是否通顺 LLM 评分

2.典型项目架构

单 Agent 应用

适用场景：工具调用型助手、单一任务系统。

多 Agent 系统

主管-工作者模式（Supervisor-Worker）

协作讨论模式（Multi-Agent Debate）

多个 Agent 对同一问题发表观点，互相辩论，最终达成更优解。

RAG 应用演进路径

Agentic RAG：用 Agent 的方式做 RAG，模型自主决定检索什么、用什么关键词、是否需要多次检索、是否需要查阅更多信息。

3.生态扩展

LangGraph

LangGraph 是 LangChain 生态的扩展，用于构建有状态、多角色的 LLM 应用，支持循环和条件分支。

LangGraph 适用场景：

  • 需要循环/迭代的工作流（如自我反思、迭代优化）
  • 多 Agent 协作与编排
  • 复杂的条件分支逻辑
  • 需要状态管理的长流程

与 LlamaIndex 对比

维度 LangChain LlamaIndex
定位 通用 LLM 应用框架 数据优先的 RAG 框架
核心优势 链/代理/工具生态丰富 数据索引与检索能力强
数据连接 丰富但偏通用 更深入（支持更多数据源）
Agent 能力 强（多种 Agent 类型） 弱
适用场景 通用 LLM 应用、Agent 系统 知识库问答、RAG 应用

互补使用：实际项目中可以两者结合，用 LlamaIndex 处理数据索引和检索，用 LangChain 做链编排和 Agent 逻辑。
