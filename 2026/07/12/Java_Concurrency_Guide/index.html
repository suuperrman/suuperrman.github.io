Java并发变成学习笔记

一、基础线程

1.线程入门

1.1 为什么学习并发

并发编程是现代软件开发的核心能力。随着多核CPU普及，单线程程序已无法充分利用硬件资源。掌握并发编程可以：

  • 充分利用多核CPU，提升程序吞吐量
  • 提高系统响应速度，改善用户体验
  • 正确处理共享资源的并发访问，避免数据不一致

注意事项：并发编程是一把双刃剑，在提升性能的同时也带来了线程安全、死锁、性能下降（上下文切换开销）等复杂问题。编写正确的并发程序比编写正确的单线程程序困难得多。

1.2 进程与线程概念、特色

进程：操作系统进行资源分配的最小单位。每个进程拥有独立的内存空间和系统资源。

线程：CPU调度的最小单位。一个进程可以包含多个线程，线程共享进程的内存空间（堆、方法区），但拥有独立的栈、程序计数器。

进程 vs 线程 对比说明：

维度 进程 线程
资源分配 最小单位 不是资源分配单位
CPU调度 不是调度单位 最小调度单位
内存空间 独立 共享进程空间
通信成本 高（需要IPC） 低（共享内存）
创建开销 大 小
安全性 进程隔离 一个线程崩溃可能影响整个进程

3.2 sleep

注意事项：sleep()不释放锁，如果有线程在sleep期间持有锁，其他等待该锁的线程无法获取锁。sleep(0)相当于让出CPU时间片。

3.3 yield

注意事项：yield()只是向调度器发出暗示，表示愿意让出CPU，但调度器可以忽略。它不释放锁，只是从运行态回到就绪态。

3.4 join

使用场景：等待子线程完成后再继续后续操作，如批量任务的结果汇总。

3.5 interrupt：两阶段终止模式

两阶段终止模式核心思想：使用interrupt()发出中断信号，线程在安全位置检查中断标志后优雅退出，避免使用已废弃的stop()（可能导致数据不一致）。

注意事项：Thread.interrupted()会清除中断标志，isInterrupted()不会清除。被InterruptedException捕获后中断标志会被清除。

3.6 守护线程

使用场景：垃圾回收线程（GC）、心跳检测、日志刷盘等不需要正常退出的后台任务。

注意事项：守护线程中的finally块不保证执行，因为JVM退出时直接终止守护线程。

3.7 线程优先级

注意事项：线程优先级高度依赖操作系统，不能作为程序正确性的依赖。大多数场景不推荐调整优先级。

4.线程运行原理

4.1 栈帧结构

每个线程有独立的虚拟机栈，每个方法调用创建一个栈帧（Stack Frame）。栈帧包含局部变量表、操作数栈、动态链接、方法返回地址。

4.2 线程上下文切换

CPU在多个线程之间轮流执行，每次切换需要保存当前线程的状态（程序计数器、栈帧信息等），并恢复目标线程的状态，这个过程称为上下文切换。

注意事项：上下文切换是有开销的（通常几微秒），对于执行时间极短的任务，多线程可能比单线程更慢。IO密集型任务适合多线程，因为线程等待IO时会释放CPU。

二、线程安全

1.线程安全问题

1.1 临界区

临界区（Critical Section）是指访问共享数据的代码段，多个线程同时执行临界区代码会导致数据不一致。

1.2 竞态条件

竞态条件（Race Condition）是指程序的结果依赖于多个线程的执行顺序。当多个线程在临界区交叉执行时，结果可能不确定。

注意事项：竞态条件的核心问题是”先检查后执行”（check-then-act）不是原子操作，需要同步机制保证。

2.synchronized内置锁

2.1 synchronized理解

synchronized是Java内置的锁机制，保证同一时刻只有一个线程可以执行被保护的代码段。

2.2 锁对象面向对象改进

注意事项：使用私有锁对象比锁this更安全，防止外部代码通过获取同一锁对象来干扰同步逻辑。字符串常量不能作为锁对象（池化导致多个不相关的代码块共享同一锁）。

2.4 Monitor管程工作原理

Monitor（管程/监视器锁）是synchronized的底层实现。每个Java对象都关联一个Monitor。

Monitor核心字段：

  • _owner：指向持有Monitor的线程
  • _EntryList：阻塞等待锁的线程队列
  • _WaitSet：调用wait()后等待的线程队列

2.5 synchronized锁优化

JDK 6对synchronized进行了大量优化，引入了偏向锁、轻量级锁、重量级锁等机制。

偏向锁

偏向锁针对第一个访问同步块的线程，将锁标记为”偏向”该线程，后续该线程进入不需要任何同步操作。

使用场景：只有一个线程访问同步块的场景（绝大多数实际场景）。

轻量级锁

当有多个线程交替访问同步块（无竞争），使用CAS操作代替重量级锁。

重量级锁

当锁竞争激烈时，轻量级锁自旋失败，膨胀为重量级锁（基于Monitor实现）。

锁膨胀、锁撤销

锁膨胀方向：偏向锁 -> 轻量级锁 -> 重量级锁（不可逆）。

自旋锁、批量重偏向

synchronized锁状态对比说明：

三、JMM Java内存模型

1.可见性

1.1 可见性问题产生

Java内存模型（JMM）规定每个线程有自己的工作内存（CPU缓存），共享变量存储在主内存中。线程对变量的操作先在工作内存中进行，无法及时对其他线程可见。

1.2 可见性解决方案

可见性解决方案：

  • volatile：轻量级，保证可见性和有序性，不保证原子性
  • synchronized：重量级，保证可见性、原子性、有序性
  • Atomic原子类：基于CAS + volatile，保证可见性和原子性

2.volatile关键字

2.1 volatile保证可见性原理

volatile变量的写操作会在汇编指令中生成lock前缀指令，该指令会：

  1. 将当前CPU缓存行的数据写回主内存
  2. 通过缓存一致性协议（MESI）使其他CPU缓存了该地址的数据无效

2.2 volatile禁止指令重排

编译器和CPU为了优化性能会对指令进行重排序。volatile通过内存屏障（Memory Barrier）禁止重排序。

内存屏障规则：

  • volatile写之前的操作不能重排序到写之后
  • volatile读之后的操作不能重排序到读之前
  • volatile写先于volatile读

2.3 DCL双重检查锁单例模式

2.4 happens-before规则

happens-before是JMM定义的偏序关系，用于判断操作之间的可见性。如果A happens-before B，则A的操作结果对B可见。

八大规则：

  1. 程序顺序规则：同一线程中，前一个操作happens-before后一个操作
  2. 锁规则：一个锁的unlock操作happens-before后面对同一锁的lock操作
  3. volatile规则：volatile变量的写操作happens-before后面对该变量的读操作
  4. 线程启动规则：Thread.start() happens-before该线程的所有操作
  5. 线程终止规则：线程的所有操作happens-before Thread.join()的返回
  6. 线程中断规则：Thread.interrupt()的调用happens-before被中断线程检测到中断
  7. 对象终结规则：对象的初始化完成happens-before其finalize方法的开始
  8. 传递性：A happens-before B, B happens-before C, 则A happens-before C

3.原子性、有序性

3.1 原子性

原子性是指一个操作或一系列操作不可分割，要么全部执行，要么全部不执行。

JMM对三种特性的保证：

特性 synchronized volatile Atomic
原子性 保证 不保证 保证
可见性 保证 保证 保证
有序性 保证 保证 保证

3.2 有序性

有序性是指程序执行的顺序按照代码的先后顺序执行。编译器和CPU可能对指令进行重排序以提高性能，但在单线程下不能改变程序结果（as-if-serial语义）。

注意事项：单线程下指令重排序不会改变结果（as-if-serial），但在多线程下可能导致可见性问题。volatile和synchronized都能保证有序性，但机制不同：volatile通过内存屏障，synchronized通过互斥锁。

2.ReentrantReadWriteLock读写锁

2.1 读写锁原理

读写锁将锁分为读锁（共享锁）和写锁（排他锁）：

  • 读锁：多个线程可以同时持有读锁（读不互斥）
  • 写锁：只有一个线程可以持有写锁（写互斥）
  • 读写互斥：读锁和写锁不能同时被持有

读写锁规则：

当前锁状态 读线程 写线程
无锁 获取读锁 获取写锁
读锁（持有） 获取读锁 阻塞
写锁（持有） 阻塞 阻塞

2.2 锁降级

锁降级是指持有写锁的线程在写操作完成后获取读锁，然后释放写锁，转为持有读锁。

注意事项：锁升级（读锁 -> 写锁）是不允许的，会导致死锁。

五、CAS与原子工具类

1.CAS原理

1.1 CAS工作方式

CAS（Compare And Swap，比较并交换）是一种无锁原子操作。CAS操作包含三个操作数：内存位置（V）、预期旧值（A）、新值（B）。当且仅当V的值等于A时，将V更新为B，否则不操作。

1.2 CAS + volatile

CAS和volatile通常配合使用：volatile保证可见性，CAS保证原子性。

1.3 ABA问题

一个值从A变为B再变回A，CAS无法检测到中间发生了变化。

七、线程池

1.线程池概念

线程池是预先创建一定数量的线程，复用线程执行任务，避免频繁创建和销毁线程的开销。

使用线程池的好处：

  • 降低资源消耗：复用线程，减少创建/销毁开销
  • 提高响应速度：任务到达时无需等待线程创建
  • 便于管理：统一调度、监控、控制线程数量

2.自定义线程池

2.1 任务队列

任务提交流程：

  1. 任务提交时，先判断核心线程是否已满
  2. 未满则创建核心线程执行
  3. 已满则放入任务队列
  4. 队列已满则创建非核心线程（直到最大线程数）
  5. 最大线程数已满则执行拒绝策略

2.2 拒绝策略

DiscardPolicy 静默丢弃新任务
DiscardOldestPolicy 丢弃队列最旧的任务，重新提交

八、AQS原理

1.AQS核心原理

AQS（AbstractQueuedSynchronizer）是JUC的核心同步框架，ReentrantLock、Semaphore、CountDownLatch、ReentrantReadWriteLock等都基于AQS实现。

核心组件：

  • state：同步状态变量（volatile int），不同实现赋予不同含义
  • CLH队列：双向链表等待队列，存储等待获取锁的线程
  • Node：队列节点，封装等待线程和等待状态

2.AQS独占模式

独占模式：同一时刻只有一个线程可以获取同步状态（如ReentrantLock）。

3.AQS共享模式

共享模式：允许多个线程同时获取同步状态（如Semaphore、CountDownLatch）。

核心方法 tryAcquire/tryRelease tryAcquireShared/tryReleaseShared
state含义 锁状态/重入次数 许可数/计数
典型实现 ReentrantLock Semaphore, CountDownLatch

十、并发集合

1.ConcurrentHashMap

1.1 HashMap死链回顾

JDK 7的HashMap在多线程并发扩容时可能产生循环链表（死链），导致get操作进入死循环（CPU 100%）。

1.2 JDK7：Segment分段锁原理

JDK 7的ConcurrentHashMap采用分段锁（Segment）设计，将整个Map分成多个Segment（默认16个），每个Segment是一个独立的HashMap，拥有自己的锁。不同Segment的操作可以并发执行。

优点：不同Segment并发操作，提高吞吐量。
缺点：并发度固定（16），Segment数组不能动态扩展。

1.3 JDK8：get、put、transfer、size原理

JDK 8的ConcurrentHashMap废弃了Segment，采用Node数组 + CAS + synchronized实现。

JDK 7 vs JDK 8 ConcurrentHashMap 对比说明：

维度 JDK 7 JDK 8
锁粒度 Segment（段） Node（桶）
锁实现 ReentrantLock CAS + synchronized
并发度 固定16 数组长度（可动态扩展）
数据结构 数组+链表 数组+链表+红黑树
查询效率 O(n) O(log n)（红黑树）

3.CopyOnWriteArrayList写时复制集合

CopyOnWriteArrayList特点：

  • 读操作完全无锁，性能极高
  • 写操作加锁并复制整个数组，写性能差
  • 最终一致性：读到的可能是旧数据
  • 不会抛出ConcurrentModificationException

适用场景：监听器列表、配置缓存、白名单/黑名单等读多写少的场景。
